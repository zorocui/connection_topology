# 批量采集失败明细与失败重试设计

## 背景

当前设备管理页能够创建全部设备、指定集群和导入首次扫描批次，并显示等待、执行中、成功和失败数量。系统已经在 `ScanTask` 中保存设备、任务状态、错误信息和执行时间，但批次页面只展示汇总，无法在数百台设备并行采集时定位失败设备及失败原因。

## 目标

- 批次执行过程中实时查看失败设备和失败原因。
- 批次完成后仍可回看失败明细。
- 支持搜索和分页，适用于数百至上千台设备。
- 支持把当前失败设备创建为新的重试批次。
- 保留原批次历史，不因重试覆盖原结果。

## 不在本次范围

- 不导出 Excel 失败报告。
- 不引入 WebSocket、SSE 或跨进程消息系统。
- 不保存异常堆栈或向页面暴露内部异常。
- 不新增失败快照表，也不复制设备资料到批次成员表。

## 总体方案

复用现有 `ScanBatchItem`、`ScanTask`、`Device` 和 `Cluster` 数据，通过分页接口实时读取指定批次的失败成员。前端只在失败明细面板打开且批次仍未完成时轮询，避免所有批次同时产生查询。

新增 `ScanBatchType.RETRY` 作为“失败重试”批次类型。该变化不新增数据库表或字段；重试批次继续使用现有批次及成员关系。

## 页面设计

### 批次卡片

- 保留现有批次进度、总数、等待、执行中、成功和失败统计。
- 当 `failed_tasks > 0` 时显示“查看失败明细”按钮。
- 批次列表保持紧凑，不把明细直接展开在卡片内部。

### 独立失败明细面板

点击“查看失败明细”后，在批次列表下方打开独立面板，不跳转页面。面板包含：

- 批次类型、批次编号、状态和失败总数。
- 搜索框，支持设备名称、IP、所属集群和失败原因。
- “重新采集失败设备”按钮。
- 失败明细表格。
- 上一页、下一页和页码跳转。
- 关闭按钮。

表格字段：

1. 设备名称
2. IP 地址
3. 所属集群；未分配时显示“未分配”
4. 失败原因
5. 开始时间
6. 结束时间

每页默认 20 条，可选择 10、20 或 50 条。后端强制最大每页 100 条。

所有设备、集群和错误文本在写入 HTML 前转义。时间复用系统现有北京时间格式化逻辑。

## 后端接口

### 查询失败明细

`GET /api/scan-batches/{batch_id}/failures`

查询参数：

- `page`：默认 1，必须大于 0。
- `page_size`：默认 20，必须在 1 至 100 之间。
- `q`：可选，去除首尾空格后用于模糊搜索。

查询范围：

- 只读取指定批次的 `ScanBatchItem`。
- 包含状态为 `FAILED` 或 `CANCELLED` 的成员，使明细总数与现有 `failed_tasks` 汇总口径一致。
- 关联 `ScanTask`、`Device`，并外连接 `Cluster`。
- 搜索设备名称、设备 IP、集群名称和任务错误信息。
- 使用任务结束时间倒序、成员 ID 倒序，保证分页顺序稳定。

响应结构：

```json
{
  "batch_id": 128,
  "batch_status": "running",
  "total": 18,
  "page": 1,
  "page_size": 20,
  "pages": 1,
  "items": [
    {
      "device_id": 17,
      "device_name": "应用节点-17",
      "host": "10.20.8.41",
      "cluster_name": "应用集群",
      "status": "failed",
      "error_message": "连接超时",
      "started_at": "2026-07-31T04:20:10Z",
      "finished_at": "2026-07-31T04:20:25Z"
    }
  ]
}
```

错误原因优先返回 `ScanTask.error_message`。字段为空时：

- `CANCELLED` 显示“采集任务已取消”。
- 其他失败显示“采集任务发生内部错误”。

批次不存在时返回 404 和“扫描批次不存在”。

### 重试失败设备

`POST /api/scan-batches/{batch_id}/retry-failures`

处理流程：

1. 验证原批次存在。
2. 重新查询原批次当前状态为 `FAILED` 或 `CANCELLED` 的设备 ID。
3. 去重并按设备 ID 排序。
4. 使用现有扫描队列创建 `ScanBatchType.RETRY` 新批次。
5. 返回新批次的 `ScanBatchRead`。

行为约束：

- 原批次和任务均不修改。
- 设备已删除时，由现有外键级联关系保证其不再出现在批次成员查询中。
- 设备已有等待或执行中的任务时，复用现有队列去重逻辑，并将新批次关联到活动任务。
- 原批次当前没有可重试设备时返回 409 和“该批次当前没有失败设备”。
- 队列容量不足时沿用现有 429 响应。
- 前端提交期间禁用重试按钮，避免同一次操作重复提交。

## 前端数据流

1. 页面加载批次汇总。
2. 用户点击某批次的“查看失败明细”。
3. 页面打开独立面板并请求第一页。
4. 搜索、页大小或页码变化后重新请求。
5. 批次为 `pending` 或 `running` 时，每 1.5 秒刷新当前条件和当前页。
6. 刷新后如果当前页超过新的总页数，自动请求最后一个有效页。
7. 批次变为 `completed` 或面板关闭时停止轮询。
8. 请求失败时保留已显示的数据，在面板内展示错误和手动重试入口。
9. 创建重试批次成功后显示新批次编号、刷新批次列表，并保持原失败面板可查看。

同一时间只打开一个失败明细面板。切换批次时取消旧轮询并重置搜索和页码。

## 性能

- 明细查询始终带批次 ID 和状态条件，复用 `ix_scan_batch_items_batch_status` 索引。
- 只返回当前页，不加载整个批次的失败设备。
- 搜索只在用户当前打开的批次内执行。
- 只有一个可见面板轮询；批次列表继续使用现有汇总轮询。
- 页面关闭或批次结束后不再请求明细。

## 测试

### 后端

- 分页总数、总页数和稳定排序。
- 按设备名称、IP、集群名称和失败原因搜索。
- 不返回成功、等待或执行中的成员。
- `FAILED` 和 `CANCELLED` 与批次失败汇总口径一致。
- 不同批次之间数据隔离。
- 缺失错误信息使用安全的中文默认值。
- 批次不存在返回 404。
- 重试只包含失败或取消设备。
- 重试创建新批次且原批次不变。
- 没有失败设备时不创建批次并返回 409。
- 已存在活动任务时，新批次正确关联该任务。

### 前端

- 仅失败数大于 0 时显示明细入口。
- 表格字段、搜索、分页和页码跳转。
- 设备及错误文本经过转义。
- 执行中轮询、完成后停止、关闭面板停止。
- 当前页失效时回到有效页。
- 重试提交时按钮禁用，完成或失败后恢复。
- 接口失败时保留已有数据并显示可重试错误。

### 验收

- 在浏览器中使用包含成功和失败设备的批次验证明细查询。
- 验证失败重试会创建新批次并进入现有扫描队列。
- 浏览器控制台没有新增错误。
- 完整测试和静态检查通过。
- 生成带时间戳的 Linux 部署包；不执行 Git 操作。
