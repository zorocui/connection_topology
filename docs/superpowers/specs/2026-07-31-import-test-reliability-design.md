# Excel 批量导入连接测试可靠性设计

## 目标

修复大批量 Excel 导入时，连接测试线程因数据库连接池超时而异常退出，部分设备永久停留在“待测试”、导入批次无法完成、首次自动采集永远不触发的问题。

第一阶段只解决后台可靠性。导入历史、阶段进度、失败明细和页面交互优化留到第二阶段。

## 当前问题

导入流程当前依次执行：

1. 解析 Excel 并创建设备；
2. 为每个新设备创建状态为 `pending` 的连接测试记录；
3. 使用线程池并发执行 SSH 或 WinRM 连接测试；
4. 每个线程分别读取设备参数、执行网络测试、保存结果并重新统计批次；
5. 最后一条待测试记录结束后，把导入批次标记为 `completed`；
6. 批次完成回调创建首次完整扫描批次。

网络测试阶段已经在数据库会话之外执行，但同一时间仍可能有多个线程读取或写入 SQLite。写事务等待 SQLite 写锁时会持续占用连接池连接，其他线程可能在获取连接时超时。该异常发生在连接测试结果生成之前或保存期间，当前 Future 回调只记录日志，不更新对应行状态，因此该行永久保持 `pending`。只要存在一条 `pending`，批次完成回调就不会执行。

## 方案

### 1. 数据库阶段独立限流

`ImportTestService` 增加一个只保护数据库阶段的进程内互斥门。

- `_load_target` 的数据库会话在门内执行；
- `_save_result` 和批次计数更新在门内执行；
- SSH/WinRM 网络等待不持有门，也不持有数据库会话；
- 网络连接测试继续使用现有 `IMPORT_TEST_MAX_WORKERS` 并发数。

这样只有短暂的数据库读写被串行化，网络测试仍可高并发执行。该设计避免 SQLite 写锁等待占满连接池，也不要求继续扩大连接池。

### 2. 瞬时数据库错误重试

数据库阶段通过统一执行器处理瞬时错误：

- SQLAlchemy 连接池 `TimeoutError`；
- SQLite `OperationalError` 中明确表示数据库忙或锁定的情况。

每个数据库阶段最多尝试 3 次。首次失败后等待 100 毫秒，第二次失败后等待 300 毫秒，再执行最后一次。每次尝试都重新创建会话，失败会话必须关闭并回滚。

非瞬时异常不重复执行，直接进入异常终结流程。

### 3. 每条记录必须进入终态

`test_row` 在最外层捕获未处理异常。发生异常时，使用相同的数据库限流与重试机制，把对应行更新为：

- `test_status = failed`；
- `test_message = 连接测试内部异常：<脱敏后的原因>`。

保存失败终态后重新统计批次。只要数据库恢复可用，任务就不会永久停留在 `pending`。如果数据库持续不可用，异常会被记录；服务重启后现有 `resume_pending` 机制重新提交仍为 `pending` 的记录。

密码、密钥和认证信息继续经过现有 `safe_error_message` 脱敏，不写入页面、日志或导入报告。

### 4. 批次完成与首次采集

每次成功或失败结果保存后都重新统计批次：

- `pending = 0` 时，将导入批次标记为 `completed` 并写入完成时间；
- 仅由第一个观察到状态从非完成变为完成的任务执行完成回调；
- 完成回调为所有连接测试成功的设备创建 `import` 类型首次扫描批次；
- 连接测试失败的设备保留在设备清单，但不进入首次扫描批次；
- 没有成功设备时仍创建总任务数为 0、状态为已完成的扫描批次，使流程具有明确终点；
- 现有幂等检查继续确保同一导入批次最多关联一个首次扫描批次。

### 5. 进程恢复

应用启动时继续调用 `resume_pending`：

- 重新提交数据库中所有 `pending` 连接测试；
- 对已经完成但尚未关联首次扫描批次的导入批次，再次执行幂等完成回调；
- 已成功、已失败或已关联扫描批次的记录不重复执行。

## 不采用的方案

### 只扩大数据库连接池

扩大连接池只能提高触发阈值。SQLite 写事务仍然串行，连接可能继续被写锁等待占用，导入规模增大后仍会复现。

### 降低整个连接测试线程数

把线程数降到数据库连接池大小会同时降低 SSH/WinRM 网络并发，数百台设备的连接测试耗时会显著增加。数据库阶段限流可以在保证稳定性的同时保留网络并发。

## 测试

### 单元和集成测试

- 150 条设备、20 个连接测试线程、数据库池大小 2、无溢出连接、超时 1 秒：所有记录进入成功或失败终态，批次完成；
- 同一压力配置下验证首次扫描批次自动创建；
- 1000 条设备压力场景：不存在残留 `pending`，批次完成且首次扫描批次只创建一次；
- 模拟第一次和第二次数据库连接池超时，第三次成功：最终结果正常保存；
- 模拟连接测试内部异常：对应行标记失败，批次仍可结束；
- 模拟数据库持续不可用：记录异常且服务恢复后 `resume_pending` 可以继续处理；
- 多个任务同时结束：完成回调只生效一次，不生成重复扫描批次。

### 回归检查

- 原有 Excel 格式、1000 行上限、重复设备跳过和逐行错误隔离保持不变；
- Linux 与可选 Windows 连接测试行为保持不变；
- Ruff 检查通过；
- 完整 pytest 套件通过，不再保留现有的 150 行连接池压力测试失败。

## 验收标准

- 导入 150 行设备后，不会因连接池超时永久停在“正在测试连接”；
- 每个已导入设备最终显示连接测试成功或失败；
- 导入批次最终进入完成状态；
- 所有连接测试成功的设备自动进入首次完整扫描队列；
- 首次扫描批次可以继续由现有扫描批次页面显示和跟踪；
- 网络连接测试并发能力不因修复而降低。
