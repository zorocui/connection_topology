# Excel 导入连接测试状态与页面稳定性设计

## 目标

修复设备批量导入后少量记录长期停留在“待测试”、导入批次无法完成，以及用户打开“查看逐行结果”后内容被轮询自动关闭的问题。

本次改造同时提高状态可观察性和 SSH 执行可靠性：用户能够区分尚未开始与正在执行的连接测试；单台设备命令超时后会明确失败；应用重启后能够恢复未完成任务；下载报告与页面显示使用一致的状态。

## 已确认的问题

### 1. 待测试状态同时表示排队和执行中

后台工作线程读取一条 `pending` 记录后，网络连接测试期间不会更新数据库状态。因此，正在执行甚至已经卡住的设备在页面上仍显示“待测试”，无法判断任务是否已被工作线程领取。

### 2. Linux SSH 输出读取顺序可能永久阻塞

当前实现先调用 Paramiko 的 `recv_exit_status()`，然后才读取标准输出和标准错误。Paramiko 明确说明：当远端输出超过 SSH 通道窗口时，如果输出尚未被持续读取，`recv_exit_status()` 可能一直等待，形成互相阻塞。连接很多的服务器执行 `ss` 时更容易触发该情况。

### 3. 页面轮询会重建整个导入结果区域

导入批次每 1.2 秒轮询一次。每次刷新都通过 `innerHTML` 重建结果区，导致用户刚加载的逐行结果节点被删除，所以视觉上表现为“一点开就自动关闭”。

### 4. 批次与报告缺少运行中状态

数据库、API 和 Excel 结果报告只有待测试、成功、失败和不适用，不能表达测试已开始但尚未结束。

## 状态模型

### 行级状态

`ImportTestStatus` 增加 `RUNNING = "running"`：

- `pending`：任务正在队列中等待工作线程领取；
- `running`：工作线程已经领取任务，正在执行 SSH 或 WinRM 连接测试；
- `success`：连接测试成功；
- `failed`：连接测试失败、超时或发生内部异常；
- `not_applicable`：该行未成功导入，不需要连接测试。

正常状态流转为 `pending -> running -> success/failed`。只有 `pending` 能被工作线程领取，避免重复执行。

### 批次计数

`ImportBatch` 增加 `test_running_rows`，其余计数语义保持不变：

- `test_pending_rows` 只统计等待领取的行；
- `test_running_rows` 统计正在执行的行；
- `test_success_rows` 和 `test_failed_rows` 统计终态。

当且仅当 `test_pending_rows + test_running_rows == 0` 时，批次进入 `completed`。进度按 `(成功数 + 失败数) / 已导入数` 计算；没有待测试设备时显示为 100%。

## 开发阶段数据与接口策略

当前系统仍处于开发测试阶段，本次不兼容旧数据库、旧导入批次或旧接口响应格式：

- `ImportBatch` 模型直接增加必填的 `test_running_rows` 字段；
- `ImportTestStatus` 直接增加 `running` 状态；
- API 响应直接返回新的运行计数，不提供旧字段组合或版本分支；
- 页面和 Excel 报告只按新格式处理；
- 实施完成后重建当前开发数据库，由 SQLAlchemy 按最新模型创建表结构；
- 不编写从旧版导入表到新版导入表的数据迁移，也不保留现有导入记录。

重建数据库前只确认并删除项目实际配置使用的开发数据库文件，不操作项目目录外或路径不明确的数据库。设备、集群和历史连接等当前测试数据也会随开发数据库一起清空。

## 后台任务处理

### 原子领取任务

`_load_target` 在现有数据库串行门内执行以下操作：

1. 读取行记录并确认状态为 `pending`；
2. 将其改为 `running`，测试说明改为“正在测试连接”；
3. 重新统计批次各状态数量并提交事务；
4. 返回脱离数据库会话的设备连接参数。

网络连接仍在数据库会话和数据库串行门之外执行，因此不会降低 SSH/WinRM 并发能力。

### 保存终态

正常结果只把 `running` 更新为 `success` 或 `failed`。为覆盖领取阶段自身发生异常的兜底路径，内部异常保存允许把尚未成功领取的 `pending` 直接更新为 `failed`。每次保存后重新统计批次；只有首次把批次推进到完成状态的线程触发首次自动采集回调。

### 进程重启恢复

应用启动执行 `resume_pending` 时，把数据库中遗留的全部 `running` 行视为上一次进程中断造成的失联任务，先统一恢复为 `pending`，重新统计受影响批次，然后提交并重新入队。已成功、已失败和不适用的行不重复测试。

该恢复能力只保证同一新版数据结构中的正常进程重启，不读取或转换旧版批次。当前旧数据库中的 14 条 `pending` 记录会随开发数据库重建而清除，需要使用原 Excel 重新导入进行验证。

## Linux SSH 命令执行

### 持续排空通道

不再先等待退出码。执行命令后循环处理 Paramiko 通道：

1. 读取当前可用的标准输出数据；
2. 读取当前可用的标准错误数据；
3. 检查远端是否已给出退出状态；
4. 远端退出后排空剩余数据，再获取退出码；
5. 未结束时短暂让出线程并继续循环。

这样不会因输出超过 SSH 通道窗口而让远端和本地互相等待。字节流在完成后统一按 UTF-8 解码，无法解码的字符继续使用替换策略。

### 总执行超时

从命令开始时使用单调时钟计算总截止时间，默认沿用当前 collector 的 15 秒超时配置。超过截止时间时关闭通道并抛出 `CollectorError("command_timeout", "远程 ss 命令执行超时")`，导入行随后进入 `failed`，页面和报告显示脱敏后的明确原因。

`exec_command` 自身的 socket 超时、Paramiko 异常和操作系统超时继续转换为现有错误类型。客户端始终由现有 `finally` 关闭。

## 页面交互

### 进度摘要

导入结果摘要增加：

- 等待测试；
- 正在测试；
- 测试成功；
- 测试失败；
- 完成百分比和进度条。

状态名称继续全部使用中文，SSH、WinRM 等专业术语保持原样。

### 保留逐行结果

页面在 JavaScript 中保存当前已展开批次的标识和逐行结果 HTML。轮询重绘批次摘要时重新挂载该内容，而不是创建空容器覆盖它。批次完成后的最后一次刷新同样保留展开内容。

逐行状态映射增加“正在测试”。用户再次点击“查看逐行结果”时重新请求最新数据，便于观察状态变化。

### 下载报告

Excel 报告的连接测试状态增加“正在测试”。等待队列中的行仍显示“待测试 / 导入成功，等待连接测试”；已被领取的行显示“正在测试 / 正在测试连接”；终态显示实际成功或失败原因。

## 测试策略

### 数据与任务状态

- 从 `pending` 领取任务后立即变为 `running`，批次等待数减少、运行数增加；
- 成功和失败结果从 `running` 正确进入终态；
- `pending + running` 任一非零时批次不能完成；
- 最后一条运行任务结束后批次完成，首次采集回调只触发一次；
- 启动恢复把遗留 `running` 重置并重新提交；
- 新版进程重启后，遗留 `running` 能恢复为 `pending` 并最终结束；
- 新建数据库直接包含运行计数列，不执行旧数据迁移。

### SSH 通道

- 模拟大输出通道，验证在调用 `recv_exit_status()` 前已持续读取标准输出和标准错误；
- 模拟分块到达的数据，验证输出完整拼接；
- 模拟一直不退出的命令，验证总超时、通道关闭和 `command_timeout`；
- 现有认证失败、命令不可用与降级采集测试保持通过。

### 页面与报告

- 页面包含等待、运行、成功、失败及进度字段；
- 轮询重绘逻辑保留已展开的逐行结果；
- 行状态映射包含 `running: "正在测试"`；
- Excel 报告分别输出待测试和正在测试；
- 完整 pytest 与 Ruff 检查通过。

## 验收标准

- 导入 148 台设备时，页面能明确区分排队和正在测试的设备，不再把执行中任务伪装成待测试；
- 单台 Linux 设备输出很大或命令不结束时，最多等待配置的命令超时时间，然后明确标记失败，不会让批次永久卡住；
- 新版服务异常重启后，新格式批次的待测试和遗留运行中任务能自动恢复；
- 打开逐行结果后，后台轮询不会再自动关闭内容；
- 批次最终进入完成状态，并按原流程为连接测试成功的设备触发首次自动采集；
- 开发数据库重建后，使用原 Excel 重新导入 148 台设备，全部测试任务最终进入成功或失败终态。
